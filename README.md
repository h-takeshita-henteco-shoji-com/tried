# tried

AIを使って何かを「やってみた」記録を、1日1件ずつ残すリポジトリです。
やってみたことは、技術文章として一般公開します。

このREADMEは、活動の履歴をどう管理するかの方針をまとめたものです。

## 結論

このリポジトリを記録の「正本」とします。
記録は1日1フォルダで残します。
テーマの候補と進み具合は、GitHub Issuesで管理します。
公開記事は、正本から書き出す「出力」と位置づけます。

## なぜこの形にするのか

毎日続ける活動は、記録の手間が小さいほど続きます。
また、公開先は将来変わる可能性があります。
この2点から、次の3つを満たす形を選びました。

- **公開先に依存しない。** 記事をMarkdown(記法つきのテキスト)で手元に持ちます。公開先を変えても履歴が残ります。
- **AIに作業を任せやすい。** ファイルの形なら、AIが記録の作成から記事の下書きまで一気に行えます。
- **試した物も一緒に残せる。** コード、指示文、画面写真を記事と同じ場所に置きます。後から再現できます。

## 他の方法との比較

| 方法 | 良い点 | 弱い点 |
|---|---|---|
| GitHubリポジトリ(採用) | 変更履歴が自動で残る。AIと相性が良い。 | 最初に型を決める必要がある。 |
| Notionなどのデータベース | 一覧や絞り込みが見やすい。 | 試したコードを一緒に置きにくい。 |
| 公開サービスだけで管理 | 手間が最小。 | 未公開の日や失敗の記録が残らない。 |
| スプレッドシート | 集計が簡単。 | 本文や成果物を置けない。 |

## 記録の3層

記録を3層に分けます。
混ぜると「書けない日」に活動全体が止まるためです。

| 層 | 役割 | 置き場所 |
|---|---|---|
| テーマ | やってみたいことの候補と、その進み具合。 | GitHub Issues |
| 実施記録 | その日のメモ、指示文、成果物。 | `年/月-日-主題/` |
| 公開記事 | 実施記録から書き起こした記事。 | 各フォルダの `article.md` |

## テーマはIssuesで管理する

テーマの候補はファイルではなくGitHub Issuesに起票します。
1件のテーマが「候補→実施→執筆→公開」と段階を進む管理は、ファイルの箇条書きでは追いにくいためです。

- **1テーマ1Issue。** 本文に「何を試すか」「なぜ気になるか」を書きます。
- **状態はラベルで持つ。** `候補` `実施中` `執筆中` `公開済` の4つを付け替えます。
- **公開したらcloseする。** closeの日時が投稿日の記録になります。
- **機密を入れない。** リポジトリは公開のため、Issuesも公開されます。

### 大きいテーマは親子に分ける

1日で終わらないテーマは、親Issueと子Issueに分けます。
「1日1件」の単位を子Issueに固定し、1日の作業量をぶらさないためです。

- **親は目的と全体の学びを持つ。** 親はフォルダを持ちません。GitHubのサブイシュー機能で子を紐づけます。
- **子は1日1件、1フォルダに対応する。** フォルダ名は `月-日-親の主題-連番-子の主題` とします。
- **子は事前に全部作らない。** 最初の2〜3件だけ作り、やりながら足します。
- **親は子が全部closeした日にcloseする。** その日に親のまとめ記事を書きます。
- **1日で終わるテーマは単独Issueにする。** 親子は複数日かかるものだけに使います。

## フォルダの構成

```
tried/
├── README.md             この文書
├── INDEX.md              一覧表(自動で生成)
├── .claude/commands/     Claude Codeに登録した定型手順
└── 2026/
    ├── 10-02-主題/              単独テーマ
    │   ├── log.md               実施記録
    │   ├── article.md           公開記事
    │   └── assets/              画面写真、コード、指示文
    └── 10-03-親の主題-01-子の主題/   親子テーマの子
        └── (同じ構成)
```

## 記録に付ける項目

各 `log.md` の先頭に、決まった項目を付けます。
後で一覧や集計を自動で作るためです。

```yaml
---
date: 2026-10-02
title: 主題
issue: Issue番号
parent: 親Issue番号(単独テーマなら空)
ai: 使ったAI
minutes: 所要時間(分)
result: 成功 / 失敗 / 途中
status: 未公開 / 公開済
url: 公開先のURL
---
```

本文は、最低限つぎの3点を書きます。

1. 試したこと
2. 結果
3. 学び

## 一覧表は自動で作る

一覧表(`INDEX.md`)は手で更新しません。
手で更新する一覧は、必ず実態とずれるためです。
上の項目とIssueの一覧から、目次と連続日数を生成します。

## 1日の流れ

毎日の判断を減らすため、流れを5段階に固定します。
手順2と5はClaude Codeの定型手順にしてあります。

1. **選ぶ。** `候補` のIssueから1件選び、所要時間の上限を決めます。前夜に決めておくと朝に迷いません。
2. **準備する。** `/start-day Issue番号` で日付フォルダと `log.md` の雛形を作ります。ラベルが `実施中` になります。
3. **試す。** 時間内で実施し、指示文と画面写真を `assets/` に置きます。気づきは `log.md` にその場で書きます。
4. **書く。** `log.md` の3点からClaudeに `article.md` を下書きさせ、自分で直します。書けない日は3点だけで1件と数えます。
5. **投稿する。** noteに貼って公開し、`/publish Issue番号 URL` でURLの書き戻し、Issueのclose、commitとpushを行います。

テーマの起票は `/new-theme` で行います。単独・親・子のいずれも作れます。

## 使うAIの方針

「記録と執筆に使うAI」と「試す対象のAI」を分けて考えます。
役割が違うためです。

### 記録と執筆はClaudeに固定する

Claude Code(ファイルを直接操作できるAI開発ツール)が、この形と相性が良いためです。

- **ファイルを直接読み書きできる。** フォルダ作成、記録の記入、一覧の更新を一度の指示で済ませます。
- **決まった手順を登録できる。** 「今日の記録を始める」などの手順を保存し、毎日同じ指示を書く手間をなくします。
- **GitHubへの保存とIssue操作まで任せられる。** 履歴の保存、Issueの起票とclose、公開用の書き出しを手作業なしで行います。

コードを伴わない日は、Cowork(Claudeのデスクトップ作業機能)でも同じことができます。

### 試す対象は1つに絞らない

毎日続けると、題材が1つのAIの範囲に偏りがちなためです。

- **題材が広がる。** 画像生成、音声、検索特化型など、用途ごとに対象を変えます。
- **比較記事が書ける。** 同じ課題を複数のAIで試すと、それだけで1本の記事になります。
- **記録の形は変わらない。** 項目に「使ったAI」があるので、どのAIでも同じ型で残せます。

## 運用のルール

- **機密を入れない。** 顧客案件に関わる内容は公開できません。公開してよい物だけをこのリポジトリとIssuesに置きます。
- **「一投稿」の最低ラインを低くする。** 毎日長文は続きません。「試したこと・結果・学び」の3点だけでも1件と数えます。
- **失敗の日も記録する。** 連続が途切れず、記事としても価値が出ます。

## 公開先

公開先はnote(文章の投稿サービス)とします。
技術者に限らず、経営者や非技術者にも読んでもらうためです。

noteにはGitHubと連携する仕組みがありません。
そのため、公開は次の手順で手作業で行います。

1. `article.md` を書き上げる。
2. noteの投稿画面に本文を貼り付ける。
3. 見出し、画像、コードの表示を整える。
4. 公開する。
5. `/publish` で公開先のURLを `log.md` に書き戻し、Issueをcloseする。

### noteに合わせた書き方

noteは表や複雑な記法をそのまま表示できません。
貼り付け後の手直しを減らすため、`article.md` は次の形で書きます。

- **表を使わない。** 比較は箇条書きか画像にします。
- **見出しは2段までにする。** noteの見出しは大・小の2種類のためです。
- **専門用語に言い換えを添える。** 読者に非技術者が含まれるためです。
- **コードは短く抜粋する。** 全文はこのリポジトリに置き、記事からリンクします。
