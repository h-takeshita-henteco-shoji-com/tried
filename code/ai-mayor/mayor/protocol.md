# AI市長の判断の型

版: v1.4(2026-10-24、#103)。基準の市長とAI市役所を比べる前に、「試し」の決まりを足しました(3の「分からないことを試して確かめる」)。

- 効き目が分からない施策は、仮説・測る数・場所・基準を書いた「試し」として打つ
- 分からないことを「分からないことの一覧」に残し、月例ごとに1件を試しで確かめる
- 「〜を見てから」と書くなら、何を、どの道具で、いつ見るかを同じ行に書く

効き目の分からない手を様子見で続けると、何か月も確かめられないためです。

v1.3(2026-10-21、#92)では、4人を比べる前に、記録を3つ足しました。

- 答え合わせに、外れた理由の見立てと、施策の次の扱いを書く。当たり外れだけでは、次の判断に効かないため
- 施策を「施策の一覧」に1行ずつ書く(分野、公約、捨てるもの、費用)。市長どうしで数えて比べるため
- 月例ごとに「考えたが打たなかった手」を書く。捨てたのか、考えて見送ったのかを分けるため

v1.2(2026-10-21、#87)では、市長の定義に「捨てるもの」を足し、施策ごとに捨てるものとの関係を書くようにしました。
v1.1(2026-10-16、#73)では、v1(2026-10-15、#72)に試運転の途中で分かった2点を足しました。

- 施策を打つ前に、`explain` で何をするか(`action`)となぜするか(`reason`)をゲーム画面に出す
- ゲームのダイアログ(破産の警告など)を、見回りの境目に入れる
- AI市長をサブエージェント(`.claude/agents/ai-mayor.md`)で、1か月ずつ動かす

AI市長(Claude)は、この型どおりに街を見て、決めて、記録します。
型をそろえる目的は、試運転や市長どうしの比較で条件をそろえることです。
性格を与えるときも、この型は変えません。変えるのは市長の定義(性格と公約)だけです。

## 要点

- 市長は、人が先に決めた性格と公約を持って就任する。公約は任期中に変えない
- 判断は3種類。1か月ごとの「月例」、10日ごとの「見回り」、境目を越えたときの「臨時」
- 月例では、決まった順に8つの道具で街を見る。見回りでは2つだけ
- 1回の月例で打てる施策は3件まで。税と予算は少しずつ動かす
- 施策ごとに「予想」を書き、翌月に答え合わせをする。「次にやること」が実行されたかも確かめる
- 効き目が分からない施策は「試し」として打ち、仕組みに近い数で確かめる。分からないことは一覧に残す
- 建てる前に維持費を見積もり、建てた後につながったかを確かめる
- 施策を打つ前に、`explain` で理由をゲーム画面に出す。見ている人が判断を追えるようにする
- 考える間はゲームを止めておく。月例の初めに保存する

## 1. 判断の区切り

### なぜ3種類か

1か月ごとだけだと、停電や赤字に最大30日気づけません。
出来事ごとだけだと、判断の回数が読めず、費用と比較の条件がぶれます。
そこで、重い判断は月1回に固定し、軽い見回りで急ぎの件を拾います。

`advance` は途中で止まらないため、出来事で即座に止めることはできません。
代わりに、1か月を10日ずつ3回に分けて進めます。

### 1か月の流れ

1. 月例の判断をする
2. `advance(10)` → 見回り
3. `advance(10)` → 見回り
4. `advance(10)` → 次の月例へ

10日は約25秒です(#70 では30日で約74秒)。

### 見回り

急ぎの件があるかだけを確かめます。施策は打ちません。

- 見るもの: `city_info` と `events` の2つ
  - `city_info` の `citizensWithoutService` で、電気・水・下水が来ない市民の数も見る(#82 で足した)
- 臨時に切り替える境目(どれか1つに当たったら)
  - 所持金が10,000を下回った
  - 週の収支が、前回の見回りより悪化して赤字になった
  - 人口が、前回より5%以上減った
  - 幸福度が、前回より10以上下がった
  - `events` に、火事、病気、停電、断水、ごみ、犯罪、渋滞のつぶやきが3件以上ある
  - `city_info` の `citizensWithoutService` のどれかが、前回より増えた
  - `city_info` の `dialog` に、ダイアログが出ている。`advance` が `dialog` を返して止まったときも同じ
    - 人口の節目のお知らせは MOD が閉じる(`autoClosed: true`)。境目に数えず、ノートに1行残す(#82)
- 当たらなければ、ノートに数字を1行だけ残して進めます

### 臨時

見回りで境目に当たった件だけを手当てします。

- 見るもの: 原因を探すのに要る道具だけ。`complaints` と `services` から始める
- 施策は1件まで
- 次の月例で、臨時の施策も答え合わせをする

## 2. 月例で見るもの

### なぜ順番を固定するか

見る順が変わると、何に気づくかも変わります。市長どうしを比べるとき、条件がそろいません。
数字から入り、人の声で確かめ、最後に画面で場所を見ます。

### 順番

| 順 | 道具 | 見る点 |
|---|---|---|
| 1 | `city_info` | 人口、所持金、週の収支、需要、幸福度 |
| 2 | `economy` | 今の税率と予算 |
| 3 | `services` | 足りないサービスと余っているサービス |
| 4 | `citizens_summary` | 失業、学歴、健康、電気や水が来ない人の数 |
| 5 | `complaints` | 困りごとの種類と、いちばん多い場所 |
| 6 | `citizen_voices(5)` | 5人の市民の暮らし |
| 7 | `events` | 前回からのつぶやき |
| 8 | `screenshot` | 困りごとの多い場所を、引き2000〜3000で1枚 |

数字の表の1行を埋めるには、1〜5の道具を呼ぶ必要があります。表を埋めることで、見落としを防ぎます。
指示だけでは、AIは決まった確認を省きがちです(CivBench)。

調べる道具(`economy_breakdown`、`traffic`、`zones_at`、`buildings_near`、`height_at`、`list_*`、`latlon_to_game`、`move_camera`)は、必要なだけ使ってかまいません。
渋滞は `events` にも `complaints` にも出にくいです(#73)。画面で車が詰まって見えたら、`traffic` で数字を確かめます。

## 3. 動かしてよい範囲と回数

### なぜ上限を設けるか

一度に多く変えると、どの施策が効いたのか分からなくなります。
答え合わせができないと、ノートが上達につながりません。

### 上限

- 施策は、月例で3件まで、臨時で1件まで
  - 施策とは、1つの目的のための操作のまとまりです
  - 例: 「住宅地を広げる」= 道路を引く + 区画を指定する。これで1件
- 税は、1回に1種類あたり±2ポイントまで
- 予算は、1回に1サービスあたり±20ポイントまで
- 政策の変更は、月例で1つまで
- 政策をかける前に、`list_policies` の `costPerWeek` で週の費用を見積もる。費用は建物の数に比例し、街が育つと増える(#82)
- 建設費の合計は、判断の時点の所持金の半分まで
- 建てる前に、週の維持費を `list_building_types` の `upkeepPerWeek`(線は `list_net_types` の `upkeepPerWeekPerKm`)で見積もる。維持費の増え分は、週の収支の黒字の範囲に収める
- 骨格(九州自動車道)は消さない
  - JR鹿児島本線と西鉄天神大牟田線は、2026-10-16(#73)に骨格から外した。費用なしで引いた線路にも維持費がかかり、週の支出3,937を占めていたため。鉄道を引くかは市長が決める
- 取り壊し(`bulldoze`、`remove_line`)は、理由をノートに書いてから行う

### 分からないことを試して確かめる

効き目が分からない手を「様子を見る」で続けると、何か月たっても分からないままです。

- 効き目が分からない施策は「試し」として打つ。試しには、次の4つを書く
  - 仮説: 何が、何を通じて、何に効くか。例: 学校を足すと、この地区の失業が減る
  - 測る数: 道具と項目。仮説に近い数にする。例: `land_value` の円の平均、`demand_breakdown` の学歴ごとの失業
  - 場所: 測る範囲。座標と半径か、地区で書く
  - 基準: 打つ前に、同じ道具・同じ範囲で測った今の値
- 測る数は、街全体の数(人口、働き口の合計、L3 の総数)にしない。ほかの施策の効き目が混ざるため
- 結果の数(乗客、利用者)が効き目の数と同じとは限らない。何を通じて効くかの見立てを書き、それに近い数を測る
- 試しの場所では、その月に試しのほかの施策を打たない。ほかの施策を打つなら、場所を分ける
- 試しは施策の上限(月例3件)の中で数える
- 翌月の答え合わせで、測る数を基準と比べ、効いた / 効かない / まだ分からない を書く
  - 「まだ分からない」が2回続いたら、測る数か場所か打ち方(数、間隔、規模)を変えて試し直す。試し直さないなら、その理由を書く

#### 分からないことの一覧

月をまたぐ記憶は市政ノートだけです。分からないことを一覧に残さないと、翌月の判断で忘れます。

- 市政ノートの「分からないことの一覧」に、1行に1つ書く。何が分からないか、いつ書いたか、確かめた試し、結果
- 答え合わせで「まだ分からない」と書いた施策や、「原因は分からない」と書いた事実は、一覧に足す
- 一覧に残っている項目があれば、月例ごとに1件を試しにする。選ばなかった項目には理由を書く
- 確かめ終えた項目は消さず、結果の欄を埋めて残す

#### 「見てから」と書くとき

- 「〜の効き目を見てから」「様子を見る」と書くなら、何を、どの道具で、どの範囲で、いつ見るかを同じ行に書く
- 書けないなら、その手は試しにする

### 建てた後の確かめ

AIは空間の扱いが苦手です。道路につながらない区画や、電気の来ない建物を作りがちです。
建てたら、同じ判断の中で確かめます。

- 道路と区画: `zones_at` で区画が付いたか、`screenshot` で既存の道路とつながったか
- 建物: `buildings_near` で置けたか。電気や水の施設なら、次の見回りで `services` の変化を見る

### してはいけないこと

- ゲームの仕組みの外の操作(費用なしの建設 `pay=false`、お金の書き換え)
- 人にゲームを操作してもらうこと。読み込みと再起動だけは人が行う

## 4. 市政ノート

### なぜノートを残すか

判断の理由が残らないと、街の変化を後から説明できません。
予想と結果を並べておくと、AIが自分の判断を直す材料になります。

### 形式と置き場所

- 1回の運営(試運転、1人の市長の1回の街づくり)で1ファイル
- 置き場所は、その日の日付フォルダの `mayor-note.md`。画面写真は同じフォルダの `assets/`
- 雛形は `code/ai-mayor/mayor/note-template.md`
- 結果の欄には、道具が返した事実だけを書く。予想や予定と混ぜない
- 書くのは市長(AI)自身。人は書き足さない。人が手を入れたときは、その旨を記録する

### 書く時点

| 時点 | 書くこと |
|---|---|
| 就任時 | 市長の定義から、性格と公約を写す |
| 月例の初め | 前回の施策の答え合わせ(外れたなら理由の見立て、施策を続けるか・やめるか・戻すか)、試しの結果(測る数を基準と比べる)、「次にやること」を実行したか、公約の進み具合。分からないことの一覧を更新する |
| 見た後 | 見た数字(数字の表に1行)と、気づいたこと |
| 決めた後、実行の前 | 施策、どの公約のためか、捨てるものに手を出したか(出したなら理由)、理由、予想。施策と公約を `explain` の `action`、理由と予想を `reason` で画面にも出す |
| 試しを決めた後 | 仮説、測る数、場所、基準(3の「分からないことを試して確かめる」)。分からないことの一覧の、どの項目の試しか |
| 実行の後 | 道具の結果(成功・失敗、費用)。「施策の一覧」に1行足す |
| 施策を決め終えた後 | 考えたが打たなかった手と、その理由 |
| 見回り | 数字の表に1行。境目に当たったかどうか |
| 運営の終わり | 次の市長への申し送り |

### 読む範囲

ノートが長くなると、判断の文脈を圧迫します。
月例の前に読むのは、次の5つだけにします。

- 公約
- 数字の表
- 分からないことの一覧
- 直前の月例と、その後の臨時の記録
- 申し送り(前の運営から引き継いだもの)

## 5. 一時停止と保存

### なぜ止めるか

考えている間に時間が進むと、見た数字と実行するときの街がずれます。

### 手順

1. 判断の初めに `set_time(paused=true)` を呼ぶ。`advance` の後は止まっているが、念のため確かめる
2. 見る、決める、実行する、記録する
3. `advance(10)` で進める。`advance` は進めた後に自分で止まる

### 保存

保存の道具 `save_city` は #77 で足しました。

- 月例の初めに、`<運営の名前>-m<何か月目(2桁)>` の名前で保存する(例: `fukuoka-base-m07`)
  - #82 で、ゲーム内の年月では名前が重なった。1か月は30日で、月例が同じ年月に2回来ることがあるため
- 失敗した施策をやり直すためではなく、途中から比べ直すために使う
- 保存した名前を市政ノートに書く。読み込みは人が行う

| Hallucinating Splines(2026、Micropolis をAPIで操作) | 街の25%が破産。電力のつなぎ忘れ、建物の散らばり | 建設費と維持費の上限。建てた後の確かめ |

## 7. 市長の定義と公約

### なぜ公約を性格に含めるか

月例の判断は、その場で見た問題に引っぱられがちです。
人が先に公約を決めると、判断に長い軸ができます。市長どうしの差も、公約の差として比べられます。

### 決まり

- 市長の定義は、1人1ファイルで `code/ai-mayor/mayor/mayors/` に置く。雛形は `mayor-template.md`
- 定義は人が書く。中身は性格(判断の癖)、公約、捨てるもの
- 公約は3つまで。ゲーム内の道具で測れる数字と期限で書く
- 市長は公約を任期中に変えない。守れないと分かったら、その事実と理由をノートに書く
- 施策ごとに、どの公約のためかを書く。どの公約にもつながらない施策は、理由を添える
- 捨てるものは、公約のために追わなくてよいもの。手を出したときは、施策ごとにその旨と理由を書く(#87)
- 月例の答え合わせで、公約ごとに今の数字と期限までの残りを書く

### 価値観は変えない

#39 の決まりにより、現実の政治の立場の比較に見えないようにします。

- 公約は、ゲーム内の数字のどれを先に追うかで書く。「福祉を厚く」「小さな政府」のような立場の言葉は使わない
- 市長は架空にし、実在の政治家や政党に似せない

### 基準の市長

性格を与えない市長です(`mayors/base.md`)。公約は、人口・暮らし・財政の3つを同じ重みで追います。
採点は `scorecard.md` で行います(#78)。公約の達成と、どの市長にも同じ共通の採点を、分けて付けます。

## 8. 運営の回し方

### なぜサブエージェントにするか

開発の会話と同じ文脈で判断すると、市長が知るはずのない経緯まで判断に混ざります。
市長ごとに条件をそろえるため、市長の定義・判断の型・市政ノートだけを読むサブエージェントにします。
使える道具も、ゲームの道具とファイルの読み書きに絞ります。

### 1か月ずつ呼ぶ

1回で任期を全部任せると、途中で人が止められず、文脈もあふれます。
そこで、1回の呼び出しを「月例1回と見回り2回」にします。

- 親(Claude Code の会話)が `ai-mayor` を呼ぶ。渡すのは、運営のフォルダ、市長の定義、何か月目か、モデルの名前
  - 段階6の比較では、市長ごとのサブエージェント(`ai-mayor-<市長>`)を呼ぶ。市長の定義とモデルは定義に書き込んであるため、渡すのは運営のフォルダと何か月目かだけ(`compare.md`、#92)
- サブエージェントは1か月を運営し、市政ノートを書いて、親に報告する
- 親は報告を読み、人に伝えてから次の月を呼ぶ。人が止めたいときは、ここで止める
- 月をまたぐ記憶は市政ノートだけ。サブエージェントは、毎月「読む範囲」を読み直す

### 途中で親に戻るとき

- ゲームにダイアログが出た(`advance` の `dialogs`、`city_info` の `dialog`)
- ゲームの窓口につながらない。または同じ道具が3回続けて失敗した

### 画面写真

サブエージェントはシェルを持たないため、`screenshot` の `save_to` で、運営のフォルダの `assets/` に直接保存する。
