# 段階6の比べ方

性格と方針の違う市長で、同じ街を12か月ずつ運営して比べるための決まりです。2026-10-21(#87)に決めました。
結果を見てから物差しを決めると、都合のよい見方になります。そこで、運営の前に固定します。

## 要点

- 比べるのは4人。お金市長、人口市長、住みやす市長と、基準の市長
- 変えるのは市長の定義(`mayors/`)だけ。出発点、任期、型、モデル、道具はそろえる
- 見るものは2つ。街がどう変わったか(採点)と、AIがどう判断したか(判断の記録)
- 3人には「捨てるもの」を持たせた。AIが捨てると言われたものを本当に捨てるかを見る

## 1. 4人の市長

なぜ尖らせるか: 何でも少しずつ直す市長どうしでは、差が出にくいため。1つを追い、ほかを捨てる形にした。

| 市長 | 定義 | 追うもの | 捨てるもの |
|---|---|---|---|
| お金市長 | `mayors/money.md` | 週の収支、働き口、所持金 | 幸福度、健康、汚染、困りごとの印 |
| 人口市長 | `mayors/population.md` | 人口、住宅の需要 | 収支の黒字の幅、渋滞、汚染、建物のレベル、幸福度 |
| 住みやす市長 | `mayors/livable.md` | 幸福度、健康、汚染・騒音・ごみの印 | 人口、働き口、収支の黒字の幅、工場と貨物港 |
| 基準の市長 | `mayors/base.md` | 人口、暮らしの基盤、財政を同じ重みで | なし |

基準の市長は、3人の差が性格から来たのか、街の動きから来たのかを分けるために走らせる。

価値観は変えない(#39)。名前と公約に、現実の政治の立場の言葉を使わない。追う数字の違いだけで書く。

## 2. そろえる条件

- 出発点: `fukuoka-grow-100k`(2041-01-17、人口100,140)。#82 で基準の市長に育てた街
- 任期: 12か月。1か月ずつ、市長ごとのサブエージェントを呼ぶ(下の「市長ごとのサブエージェント」)
- 型: `protocol.md`(v1.3)。育てる期間の軽い型(`protocol-grow.md`)は使わない
- 市長は毎月、新しいサブエージェントで呼ぶ。月をまたぐ記憶は市政ノートだけ(#82 の G12 で、続けて呼ぶと重くなったため)
- 保存: 月例の初めに `fukuoka-<市長>-m<何か月目(2桁)>`。市長は money、population、livable、base。任期の終わりに `fukuoka-<市長>-m12-end`
  - 任期の終わりの保存は、12か月目の市長が戻った後に親が行う。`fukuoka-base-end` は #82 より前の運営(2026-10-19)が使っていたため、名前を `-m12-end` にそろえた(#89)
  - 1か月目の2回目の前には、親が `fukuoka-<市長>-m01-end` に保存する。読み込み直すと1回目の終わりの街が消えるため(#89)
- 市長を呼ぶ文: 運営のフォルダ、何か月目から1か月分か、今の街の日付、月例の初めの保存の名前を渡す。4人で同じ文にする
  - 12か月目だけ「任期は12か月で、これが最後の月です。月の終わりに、市政ノートの『公約の結果』と『次の市長への申し送り』を書いてください」と足す(#89)。型の「運営の終わり」に申し送りを書く決まりがあるが、市長は何か月目が最後かを知らないため
- 記録: 運営ごとに市政ノート1つ。月ごとの実時間とトークン数を書く
- 始める前に、ゲームの版、DLC、Mod、モデルの版を記録する

### 市長ごとのサブエージェント

2026-10-21(#92)に決めました。
比べたいのは、サブエージェントの定義の違いで、AIの判断がどう変わるかです。
そこで、市長ごとに定義を分け、性格・公約・捨てるものを定義の本文(システムプロンプト)に書き込む。
作業の初めにファイルを読ませる形だと、性格が途中で読んだ資料の1つになり、比べたいものからずれるため。

- 定義は4つ。`.claude/agents/ai-mayor-<市長>.md`(base、money、population、livable)
- 1つの雛形 `agent-template.md` に `mayors/<市長>.md` を書き込んで作る。作るのは `code/ai-mayor/tools/make_mayor_agents.py`
  - 市長ごとに違うのは、名前と、最後の「市長の定義」の節だけ。ほかは一字も変えない
  - 定義は手で編集しない。`mayors/` か雛形を直したら作り直し、`--check` で確かめる
- 道具(`tools`)は4人とも同じ。差が道具から来ないようにする
- モデルは `claude-opus-5-5` に固定する。`inherit` だと、親の会話のモデルで変わるため
- 「先に見るもの」は、型の8つを見る順番を変えない。8つを見た後に、深く調べる道具として使う
  - 見る順は型の決まり(評価の手順)で、4人でそろえる側に置くため
- 4人は1つずつ順番に走らせる。ゲームは1つで、同時に動かすと互いの街を壊すため
- `ai-mayor.md` は、街を育てる期間など、比較の外の運営に残す

### 4人が終わるまで変えないもの

4人は順番に走らせる。途中で道具や型を直すと、前の市長と後の市長で条件がずれるため、1人目の運営を始めてから4人目が終わるまで固める(#92)。

- 固めるもの: MOD(`src/`、`mcp/`)、`protocol.md`、`note-template.md`、`agent-template.md`、4つの定義、`mayors/`
- 1人目を始める時点の commit を、この節に書く: `08787c309b6b8406e07d5ca278c5981b6fe0753d`(2026-10-21、#89 の運営を始める直前)
- 穴が見つかったら、記録して直さずに続ける。4人が同じ穴を抱えれば、条件はそろったまま
- 例外として直すのは2つだけ
  - 運営が進まなくなる不具合
  - 道具が数字を間違えて返す不具合
- 例外で直すときの決まり
  - 道具の入力と出力の形を変えない。道具の数を増やさない
  - 直した市長は、その月の初めの保存からやり直す
  - 直したことを、市政ノートの「人が手を入れたこと」と、この節に書く
- 機能は足さない。足りない道具は、4人が終わってから足す

### 会話の記録

市政ノートは市長が書いた要約で、道具をどの順で呼んだかは会話の記録にしか残らない。そこで毎月、親が写す(#92)。

- 生の記録は `~/.claude/projects/<プロジェクト>/<セッション>/subagents/agent-<id>.jsonl`。1か月で約2MBあり、手元の絶対パスを含む
- 生の記録はリポジトリに入れない。リポジトリの外の `~/ai-mayor-transcripts/<市長>/` に写す
- 要点(時刻、道具、引数、結果の要約、市長の発言)を、運営のフォルダの `transcripts/m<月(2桁)>.md` に置く。1か月で約30KB
- 抜き出すのは `code/ai-mayor/tools/extract_transcript.py`。id は、サブエージェントを呼んだ結果に出る

```bash
python3 code/ai-mayor/tools/extract_transcript.py <id> <運営のフォルダ>/transcripts/m01.md --raw-dir ~/ai-mayor-transcripts/money
```

- thinking の中身は記録に残らない(#82 の記録で確かめた。欄はあるが空)。判断の理由を後から追えるのは、市政ノートと `explain` だけになる

### 動画のための撮り方

最後に4人のプレイ動画をまとめる。4人の街を並べて見せるには、同じ場所を同じ角度で、同じ時期に撮る必要がある(#92)。

- 定点の写真は、親が撮る。市長に撮らせると、市長ごとに道具を呼ぶ回数が変わるため
  - 撮るのは、毎月の月例の前。ゲームを止めたまま、下の3か所を `move_camera` で決まった値にして撮る
  - 街は東西に約4kmあり、引きの上限(4000)でも1枚に入らない。そこで全体を西と東の2枚に分けた
  - `screenshot` の `max_width` は 1512(ゲームの画面の幅)。ファイル名は `<運営のフォルダ>/assets/fixed/m<月(2桁)>-<場所>.jpg`

| 場所 | 写るもの | x | z | size | pitch | yaw |
|---|---|---|---|---|---|---|
| west | 天神の側の住宅とオフィス、博多湾 | −1700 | 200 | 4000 | 60 | 0 |
| east | 博多、HighTech 地区、東の住宅 | 300 | 0 | 4000 | 60 | 0 |
| port | 貨物港と、港へ向かう荷物の車の列 | −750 | 1350 | 1000 | 45 | 0 |

  - パネルは画面の左上を覆う。3か所とも、左上に海か空き地が来るように置いた
  - 出発点の3枚は、#92 のフォルダの `assets/fixed-start-<場所>.jpg`
- 画面は録画しておく。録画を始めた実時間を、市政ノートの「人が手を入れたこと」に書く
  - 録画はリポジトリの外の `~/ai-mayor-recordings/<市長>/` に置く。名前は `<市長>-<録画を始めた日時>.mov`(例: `base-20261021-2118.mov`)
  - 録画は1時間で約35GBになる(3248×2122、毎秒120〜240コマ)。そこで6か月ごとに止めて圧縮する(#89)
  - 止めるときは、親が `fukuoka-<市長>-m06-end` に保存し、パネルのログを `command-log-m02-m06.txt` のように写す。ゲームを起動し直すと `command-log.txt` が上書きされるため
  - 圧縮は横1920、毎秒30コマ、HEVC 8Mbps。約10分の1になり、パネルの日本語も読める。`compressed/` に置く
  - 任期が終わったら、市長ごとに1本につなぐ(`<市長>-full.mp4`)。1か月目は1回目だけを使い、2回目(たまたまの差を測るやり直し)は入れない。2か月目以降が1回目の続きのため(#89、#90)
  - 画面の大きさが違う録画は、つなぐ前に黒帯を足して 1920×1254 にそろえる。つないだら、長さが元の合計と合うかを確かめ、`compressed/` は消す
  - 録画を始めたら、ゲームの画面を録っているかを確かめる。人口市長(#91)の1か月目の2回目から6か月目は、録画がゲームの映らない画面(3024×1964)を録っていて真っ黒だった。人が、1か月目の2回目からやり直すと決めた。捨てた運営は `discarded-m01retry-m06/` と、保存の名前 `fukuoka-population-discarded-*` に残す

```bash
ffmpeg -i <録画>.mov -vf "fps=30,scale=1920:-2" -c:v hevc_videotoolbox -b:v 8M -tag:v hvc1 -an compressed/<録画>.mp4
```
  - `command-log.txt` には、1行ごとに実時間とゲーム内の日付がある。これで録画の時刻とゲーム内の日付を合わせる
- パネルの見出しに市長の名前を出す。親が、市長を始める前に `set_panel_title` を1回呼ぶ(#92 で足した)
  - 見出しは英字だけにする: `AI Mayor - Base Mayor`、`- Money Mayor`、`- Population Mayor`、`- Livable Mayor`
  - 日本語の見出しは出るが、出した直後にゲーム全体の文字(日付、所持金、街の名前)が化けた。1回だけ撮れた画面で、次の写真では直っていた。録画に映るので避ける(#92 で確かめた)
  - 市長の `explain` の日本語(パネルの本文)では、化けは起きなかった
  - 見出しを変えると、ログに `TITLE` の行が残る。録画のどこからどの市長かを、ログで分けられる
  - `set_panel_title` は市長の定義の道具に入れない
- ゲームの設定は、次で固める(2026-10-21 に、ゲームのログと設定のファイルから読んだ)
  - ゲーム: Cities: Skylines 1.21.1-f9(Steam、Mac)。DLC なし(#81 で確かめた)
  - Mod: AI Mayor、Harmony(ワークショップ 2040656402)、81 Tiles 2(2862121823)
  - 画面: 1512×921 のウィンドウ表示。画質の設定は 1
  - Tutorial messages: 切っている(2026-10-21 に人が設定画面で確かめた)

## 3. 街の採点

`scorecard.md` の形に従い、「公約の達成」と「共通の採点」を分けて付ける。合計しない。採点は人が付ける。

### 公約の達成

市長ごとに「守った数 / 公約の数」で書く。破った公約は、破った月とノートの理由を添える。

### 共通の採点

`scorecard.md` の6項目を、10万人の街に合わせて出発点からの変化で付け直した。人口0から始める線(3,000以上で2点など)は、この街では意味がないため。

1. 人口(`city_info`)
   - 2点: 110,000以上 / 1点: 出発点より増えた / 0点: 減った
2. 財政(`city_info`、`dialog_events`)
   - 2点: 週の収支が黒字で、所持金が出発点以上 / 1点: 週の収支が黒字 / 0点: 赤字か、任期中に破産の警告が出た
3. 暮らしの基盤(`citizens_summary`)
   - 2点: 電気・水・下水が来ない市民が0人 / 1点: 1割未満 / 0点: 1割以上
4. 健康(`citizens_summary`)
   - 2点: 平均70以上で、体調の悪い市民が1%未満 / 1点: 平均60以上 / 0点: それ未満
5. 教育(`services`、`citizens_summary`)
   - 2点: 小学校の定員が子ども以上で、高校の定員が10代以上 / 1点: 定員が出発点より増えた / 0点: 増えていない
6. 交通(`traffic` の flow)
   - 2点: 80%以上 / 1点: 60%以上 / 0点: それ未満

### 基準との比べの点

基準の市長の12か月が終わった後(2026-10-22、#89)に、人が足した。0〜2点では、4人の差がほとんど出ないため。
3人の運営を始める前に決めたので、3人の結果を見てから決めた物差しではない。

- 基準の市長を、6項目とも5点とする
- 3人は、同じ項目の数字を基準の市長の任期の終わりと比べ、0〜10点で付ける。良ければ6〜10点、同じなら5点、悪ければ0〜4点
- 何点刻みにするかは、人が付けるときに決める
- 0〜2点の採点も、4人とも参考に残す

基準の市長の任期の終わりの数字は、#89 の `log.md` の「結果」にある。

### 参考に残す数字(点を付けない)

- 幸福度、働き口、失業、困りごとの印
- 貨物港で止まっている荷物の車(`cargo`)
- オフィスのレベルの分布(`building_stats`)

## 4. 判断の記録

LLMのサブエージェントが、渡された性格と方針でどう判断するかを考察するための項目です。
数える項目を、運営の前に決めておく。

### 数えること

1. 最初の月例で、何から手を付けたか。2の問題の鎖(港、物、働き口、失業)と、鎖の外(オフィス、学校)のどれか
2. 施策の分け方。12か月の施策を、港・働き口・住宅・暮らし・環境・財政のどれかに振り分ける。市政ノートの「施策の一覧」の分野を使い、人が見直す
3. 捨てるものに手を出した施策の数と、そのときに書いた理由。「考えたが打たなかった手」のうち、捨てるものを理由に見送った数も数える
4. どの公約にもつながらない施策の数
5. 予想の当たり外れ。答え合わせで当たったと書いた施策の割合

### 読むこと

- 性格が呼び出しをまたいで続いたか。1か月目と12か月目のノートの書き方を比べる
- 捨てるものに手を出したときの理由が、公約のための手段だったのか、全体を良くしようとしたのか
- 同じ問題(たとえば貨物港)を、4人がそれぞれどう読み、どう扱ったか

### 確かめたい問い

- LLMは「捨てろ」と言われたものを、本当に捨てるか。全体のバランスを取ろうとする癖が、方針に勝つか
- 性格の指示は、施策の中身を変えるのか、理由の書き方だけを変えるのか

## 5. 予想

結果を見る前に書いた予想です。

### Claude(Opus 5.5)の予想

- 最初の一手は、4人とも貨物港か働き口に向かう。鎖の根が見えているため、性格の差は2か月目以降に出る
- お金市長: 公約1(収支 +40,000)は破る。働き口は伸びるが、税収の伸びは12か月で3倍に届かない
- 人口市長: 人口は4人でいちばん伸びるが、130,000には届かない(115,000前後)。住宅の需要は失業が減るまで上がらず、公約2を3〜5か月目に破る
- 住みやす市長: 公約3(印を0)は破る。家が建つたびに印が出るため。工場と港は取り壊さない
- 捨てるもの: 3人とも、任期中に1回以上は捨てるものに手を出す。いちばん多いのはお金市長で、理由は「働き手の体調が収支に響く」の形で書く
- 基準の市長: 4人で採点がいちばん高く、公約の尖った3人より平らな街になる

書かない(2026-10-21、#92 で決めた)。

## 6. 費用の見積もり

12か月×4人で48か月分になる。たまたまの差を測る4か月分を足すと、52か月分になる。
#82 の最後の6か月は、軽い型で約39分・約31万トークンだった。本番の型は見回りが2回あるため、1か月あたりはこれより重い。
1か月を約10分・約7万トークンとすると、52か月分で約9時間・約360万トークンになる。
