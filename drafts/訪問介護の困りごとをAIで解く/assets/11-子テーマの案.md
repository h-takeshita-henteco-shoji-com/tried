# 子テーマの案(1ペイン1検証、業務の流れの順)

作成日: 2026年11月8日(10件に広げ、業務の流れの順に並べ直した。技術の基盤として00を足した)

## この資料の結論

- 子テーマは10件。1つのペインを、1つの検証で確かめる。
- 選んだ基準は「ペインとして現実に存在すると強く信じられるか」。数の縛りは置かない。
- 検証の順番は、実際の業務のバリューチェーンとフローに沿わせた。相談・契約 → 計画 → 訪問の準備 → 訪問と記録 → 請求 → 賃金 → 年次の届出。
- この順にすると、架空の事業所のデータも、実際の業務と同じ順にたまっていく。
- 技術の基盤として、子テーマ00「介護報酬のルールを引けるRAG」を最初に作る。SQLiteのベクトル検索vec1を使い、別のドラフト(`drafts/SQLiteのベクトル検索vec1/`)をこの中で消化する。

ペインの詳しい根拠は `03-ステークホルダー別ペイン.md`、業務の流れは `07-訪問介護のバリューチェーン.md`、架空の事業所は `10-架空の訪問介護事業所の設計.md` にある。

## 00. 介護報酬のルールを引けるRAGをSQLiteのvec1で作る

技術の基盤になる子テーマ。01〜10の検証で、「ルールを引けるAI」と「引けないAI」を比べるために使う。

| 項目 | 内容 |
|---|---|
| ねらい | 訪問介護のルール(告示・通知・Q&A)を、根拠の箇所つきで引ける検索を作る |
| 現実の根拠 | P7(ルールの変更に追いつけない)。資料が告示・通知・Q&A・自治体の通知に分散し、改定のたびに増える |
| 検証の問い | 1. vec1で作ったRAGは、厚労省のQ&Aの問いに対し、正しい根拠の箇所を引けるか 2. 古い版の資料が混ざったとき、古いルールで答えてしまうか。版や施行日での絞り込みで防げるか |
| 使う資料(公開) | 訪問介護の単位数の告示、留意事項通知、サービス行為ごとの区分の通知、生活援助の範囲の通知、運営基準と解釈通知、介護報酬改定のQ&A、2026年6月の臨時改定の通知とQ&A、運営指導マニュアルの確認項目 |
| 使う資料(手元だけ) | 解釈本(赤本・青本・緑本、令和3年4月版)をOCRで読み取ったもの。版の違いを試す「古い資料」として使う。リポジトリに入れない |
| 作り | SQLite + vec1。各チャンクに、出典の種類・版・施行日・公開してよいかを列として持たせ、検索中に絞り込む |
| 採点 | 1. Q&Aの一部を検索の対象から外して問題にし、正しい根拠の箇所を上位10件に引けた割合(recall@10) 2. R3からR6で答えが変わった問いで、古いルールを返した割合。絞り込みの有無で比べる |
| vec1のドラフトから持ち込むもの | 速さ・準備の重さ・調整の効き方(nprobe など)の測定。sqlite-vec との比較は余力があれば行う |

### vec1のドラフトとの関係

`drafts/SQLiteのベクトル検索vec1/` の「現実の題材」と「確かめたいこと」を、この子テーマで消化する。

- 現実の題材: このリポジトリの記事検索の代わりに、介護報酬のルールを題材にする
- 規模: 公開資料だけなら数千チャンク。解釈本を足すと、vec1の学習が要る5,000件を超える見込み。学習と索引の再構築も試せる
- 列での絞り込み: vec1の「列を索引に持たせ、検索中に絞り込める」機能を、版と施行日の絞り込みに使う
- オフライン: 事業所の端末の中で引ける形にできるかは、余力があれば試す

### 注意

- 解釈本は令和3年4月版。令和6年度の改定と2026年6月の臨時改定は載っていない。今のルールの根拠には使わない
- 解釈本の検索結果や本文は、記事に載せない。載せるのは、版の違いで正答率がどう変わったかの数字だけ

## 架空の事業所のデータがたまる順

業務の流れの順に進めると、前の子テーマで作ったデータを、後の子テーマで使える。

```
01 利用者・家族・契約
 └→ 02 ケアプラン・訪問介護計画・手順書・記録
      └→ 03 提供票
           └→ 04 シフト ─→ 05 勤務表・出勤簿
                └→ 06 記録(話し言葉から)─→ 07 記録の点検・請求明細
                                            └→ 08 実績の判定
                └→ 09 1日の動き・給与 ─→ 10 処遇改善の計画と実績
```

## 手元の解釈本(赤本・青本・緑本)の扱い

### 手元にあるもの

- 介護報酬の解釈本3冊をスキャンしたPDF。赤本(単位数表編)、青本(指定基準編)、緑本(QA・法令編)にあたる
- 約4.6GB、約4,500ページ。表紙と奥付から、**令和3年4月版**と確かめた(取り込みは2025年3月)
- 文字のデータがない画像のPDF。macOSのVisionで試したところ、文字はほぼ正確に読めた。表の列の並びは崩れる。tesseractは読めなかった
- 欠けているページがある(赤本の101〜200ページ、青本の1001〜1100ページ)

### 使い方

市販本は、編集や解説に著作権がある。リポジトリもIssueも公開なので、次の線を引く。

- **手元でだけ使う。** PDFも、読み取った文字も、リポジトリに入れない
- **今のルールの確かめには使わない。** 令和3年4月版なので、令和6年度の改定と2026年6月の臨時改定が入っていない
- **RAGの「古い資料」として使う。** 子テーマ00で、古い版が混ざったときの誤りを試す
- **ルールの構造の理解に使う。** どの告示・通知・Q&Aが、どの論点に関わるかの見当をつける
- **公開する根拠は、厚労省の原文にする。** 解釈本で見つけたルールは、もとの告示・通知・Q&Aをたどり、それを出典にする
- **本文を引用しない。** 記事やリポジトリに、解釈本の文章や画面を載せない
- **比べる条件としては慎重に扱う。** 「解釈本を渡したAI」と「公開資料だけのAI」を比べるなら、結果の数字だけを書き、中身は載せない

手元での利用は、私的な複製や、情報解析のための利用の範囲で考えている。有料の記事にするなど本格的に使う前には、専門家に確かめる。

### 効きそうな子テーマ

- 00(RAG): 古い版の資料として、版の絞り込みの効き目を試す
- 01・02・07・08: ルールの構造の見当をつけるのに使う。正解の根拠は、今の版の厚労省の原文で確かめる
- 10(処遇改善): 一本化の前の版なので、使えない

### OCRの進め方

- まず訪問介護の部分だけを読み取る。赤本の単位数表と、緑本の訪問介護のQ&Aから始める
- 読み取りは手元のmacOSのVisionで行う。外部のサービスに本の画像を送らない
- 読み取った文字は、リポジトリの外に置く
