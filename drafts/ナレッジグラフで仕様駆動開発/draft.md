## きっかけ

仕様駆動開発で、設計とソースコードのつながりを漏れなく追いたい。
その情報をナレッジグラフで持てば、網羅性が上がるのではと考えた。
道具は graphify を使う。

## graphify とは

コードと文書を、AIが問い合わせできるナレッジグラフに変える道具。
Claude Code などに `/graphify` スキルとして入る。

## うたわれているメリット

graphify のREADMEが挙げる利点を、検証の観点で並べ直した。

- **関係を辿れる。** grep は文字列しか探せない。グラフなら呼び出し・import・継承を辿れる
- **設計と実装が同じグラフに入る。** 文書・SQLスキーマ・PDFもノードになる。ADRの引用やコメントの理由もコードに結び付く
- **根拠が分かる。** 各エッジに `EXTRACTED`(ソースに明記)か `INFERRED`(推定)が付く
- **コードの解析は決定的で無料。** tree-sitter のAST解析で、LLMを使わない。コードは手元から出ない
- **全体像が先に見える。** 結合の多いノード(god nodes)とサブシステムの分割を `GRAPH_REPORT.md` に出す
- **読む量が減る。** AIはファイルを読む代わりに `query` `path` `explain` で必要な部分だけ取る

自社ベンチマークでは、コードの質問の要点網羅率が 82.0% だった。
grep と read だけの場合は 70.8%。ただし問題数は6問と少ない。
自分の題材で確かめる価値はここにある。

## 検証の問い

graphify の有無で、仕様駆動開発の作業の網羅性は変わるか。

## 試したいこと(案)

まだ1つに絞らなくてよい。

- **影響範囲の調査。** 「この仕様を変えたら、どの設計とコードに響くか」を答えさせる
- **仕様と実装の対応づけ。** 要件ごとに実装箇所を挙げさせ、未実装の要件を見つけさせる
- **呼び出し経路の説明。** 画面の操作からDB更新までの経路を辿らせる

## 比べ方(案)

条件をそろえないと、違いが graphify のせいか分からないため。

- A: graphify なし。grep と read だけで答える
- B: graphify あり。`graphify claude install` でグラフを優先させる
- 同じモデル、同じ指示文、毎回新しいセッションで行う
- 1問を複数回走らせ、ぶれも見る

測るもの。

- 網羅率: 正解リストのうち、挙げられた割合
- 誤り: 挙げたもののうち、正解でない割合
- コスト: トークン数、ターン数、時間

## 気になる点

- 正解リストを先に人手で作る必要がある。ここが一番重い
- 題材は公開のコードにする。顧客案件のコードは使えない
- 仕様書を含む題材が要る。仕様駆動開発の公開サンプルを探す
- `INFERRED` のエッジが誤っていたら、逆に答えを誤らせないか
- 日本語の仕様書で `query` が効くか。中国語の分かち書きは拡張があるが、日本語は未確認
- 文書の解析だけはLLMを使う。料金と、文書がAIに送られる点に注意
- `query` の履歴が `~/.cache/graphify-queries.log` に残る
- 3日程度に分ける案: 題材と正解リストを作る → グラフを作って中身を見る → 有無で比べる
