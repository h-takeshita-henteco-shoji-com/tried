## きっかけ

SQLiteのベクトル検索拡張 vec1 が気になった。
性能を確かめ、どんな形で活用できるかを探りたい。

## vec1 とは

SQLite の開発チームが作る、ベクトル検索の拡張。
2026年2月に発表され、現在は版0.7。まだ1.0前の開発版。

- C のファイル1つで、外部依存がない。x86 は AVX2、ARM は NEON で速くする
- 仮想テーブルとして使う。`CREATE VIRTUAL TABLE t USING vec1(vector)`
- 距離はユークリッド(L2)とコサイン
- 検索方式は近似最近傍(ANN)。IVFADC と OPQ で、ベクトルを圧縮して探す
- 5,000件を超えたら、学習(`vec1_train()`)と索引の再構築が要る
- 価格や在庫などの列を索引に持たせ、検索中に絞り込める

ANN(Approximate Nearest Neighbor)は、厳密さを少し捨てて速く探す方式。

## 比べる相手

同じ問いに、作りの違う3つで答えさせる。

- **SQLite + vec1:** 今回の主役。公式の拡張で、学習が要る
- **SQLite + sqlite-vec:** 有志の拡張で、先に広まった。vec1 との差を見る
- **PostgreSQL + pgvector:** サーバー型の定番。HNSW の索引を使う

## 試したいこと(案)

まだ1つに絞らなくてよい。

- **性能を測る。** 公開データセット(SIFT や GloVe)で、再現率と速さを比べる
- **使い勝手を比べる。** 導入、学習、更新、バックアップの手間を比べる
- **現実の問題に当てはめる。** 下の題材で、本当に役に立つかを見る

## 測るもの

- 再現率(recall@10): 正しい近傍10件のうち、何件を返せたか
- 速さ: 1件の検索にかかる時間、1秒あたりの検索数
- 準備の重さ: 学習と索引作りの時間、ファイルの大きさ、メモリ
- 調整の効き方: vec1 の `nprobe` や `codesize` を変えたときの、速さと再現率の釣り合い

## 現実の題材(案)

- **このリポジトリの記事検索。** 過去の `log.md` と `article.md` から、似たテーマを探す。`/new-theme` の重複確認に使える
- **端末の中で完結する検索。** サーバーを立てられない場所で使う。手元のアプリやオフラインの環境など

## 活用先の考察(マーケットイン)

技術から用途を探すと、「オフラインでRAG」で止まりやすい。
そこで、困っている人の場面から逆にたどる。

### 前提: 位置づけの違い

- **PostgreSQL + pgvector:** サーバーにいる。常時接続が前提
- **SQLite + vec1:** 1ファイルで、端末の中で動く。通信がなくても検索できる

### オフラインで足りなくなる部品

オフラインのRAGでは、ベクトルDBだけがあっても動かない。
端末に要る部品と、その制約を並べる。

| 部品 | 役割 | オフラインでの制約 |
|---|---|---|
| ベクトルDB(vec1) | 似たものを探す | 動く。ただし1.0前で、検索は1スレッド |
| 埋め込みモデル | 問い合わせ文をベクトルにする | 端末で動かす必要がある。LLMよりは軽い |
| LLM | 探した結果から答えを書く | 端末にないか、小さく非力 |
| 索引の学習 | 5,000件超で精度と速さを保つ | 端末で行うと重い |
| データの更新 | 新しい文書を足す | 配り直しか、差分の同期が要る |
| 端末の資源 | 全体を動かす | メモリ、容量、電池に限りがある |

見落としやすいのは埋め込みモデル。
LLMを外しても、問い合わせ文のベクトル化は端末で要る。

### 制約をほどく4つの型

必要な部品を減らすほど、オフラインで動かしやすい。

- **型A: 検索だけ、埋め込みも不要。** 項目どうしの類似は、ベクトルを事前に計算して配れる。「この部品に似た部品」など
- **型B: 検索と埋め込みモデル。** 自由な文で探すが、答えは文書の抜粋を返す。LLMは使わない
- **型C: 検索と端末の小さなLLM。** 抜粋を短くまとめる程度に使う。OSに載る小型モデルなど
- **型D: 検索は端末、生成はクラウド。** 文書は端末から出さない。必要な断片だけ送るか、通信が戻ってから生成する

もう1つの工夫は、重い処理をサーバーに寄せること。
学習と索引作りはサーバーで行い、出来たファイルを配る。
1ファイルで完結する SQLite の強みが生きる。

### 適用できそうな場面

| 場面 | 困りごと | オンラインで困る理由 | 型 |
|---|---|---|---|
| 地下やトンネル、プラントの点検 | 手順書や過去の不具合事例を探せない | 電波が届かない | B |
| 船舶、航空機、山間部の保守 | 同上 | 通信が高いか、ない | B |
| 災害時の避難所 | 防災情報や支援制度を探したい | 回線が落ちる | B, C |
| 客先や機内での営業 | 製品カタログから合う品を探す | 通信が不安定。客先の回線を借りにくい | A, B |
| 店舗の端末(キオスク) | 似た商品を薦めたい | 回線が落ちても止めたくない | A |
| 医療や法務の文書 | 機密の文書を意味で探したい | 外に出せない | B, D |
| 個人のメモや写真 | 手元のデータを意味で探したい | 他人のサーバーに預けたくない | B, C |
| 開発者のツール | 手元の文書の重複や類似を見つけたい | サーバーを立てるほどではない | A, B |

### 合うかの見分け方

次の問いに「はい」が多いほど、vec1 が向く。

- 通信がない、または高い場面で使うか
- データを外に出せないか
- データは端末に載る量か
- 更新は日に1回などで、頻繁でないか
- 答えは「該当箇所を見せる」で足りるか(生成が要らないか)

逆に、書き込みが多い、複数人で同時に更新する、という場面は PostgreSQL が向く。

### 確かめたいこと

- 埋め込みモデルを手元で動かすと、問い合わせ1件に何秒かかるか
- 型Bの「抜粋を返すだけ」で、利用者は満足できるか
- サーバーで作った索引ファイルの大きさ。配れる大きさか
- 上の場面から1つ選び、小さな試作を作る

## 気になる点

- 1.0前なので、仕様が変わるかもしれない。試した版と日付を記録する
- vec1 はまだ、検索を複数スレッドで並べられない。pgvector と速さを比べるときは条件をそろえる
- 学習用のデータが、本番のデータに似ている必要がある。データが増えたら学び直しが要るか
- 圧縮すると精度が落ちるため、結果の並べ直し(rerank)がほぼ必須とされる
- 埋め込みのモデルを選ぶ。日本語の記事なら日本語に強いモデルが要る。手元で動かすか、APIを使うか
- 子に分ける案: vec1 を動かして公開データで測る → pgvector・sqlite-vec と比べる → 活用先を考察する → 場面を1つ選んで試作する
