## 試したこと

LibreCAD（図面を描くソフト）を改造する。
MCP（AIと外部ソフトをつなぐ仕組み）経由で操作できるようにする。
LLM（文章で指示を受けるAI）に、間取り図の作図と修正を任せる。

- 時間の上限は60分。

- LibreCAD 本体は組み立てず、plugin の仕組みを使った。Issue の「元のLibreCADを組み立てる」から変えた。
  - 同梱の Qt が 5.15.19 で、brew の qt@5 と同じ版だったため。plugin だけ作れば、図面の中身を直接操作できる。
- 構成は、LibreCAD の中の plugin(TCP 7471 で待つ)と、Python の MCP server の2つ。手順は `code/librecad-mcp/README.md`。

## 結果

採用した版: LibreCAD 2.2.1.6(mac、arm64)、Qt 5.15.19、mcp(Python)2.3。

1. 線を1本描き、座標を取得し、保存できた(`results/first-line.dxf`)。
   - ezdxf で開くと LINE (0,0)→(3600,0)、画層 0。
2. Sonnet に MCP だけで部屋を描かせた(`results/prompt-room.txt`)。
   - 1回目は描かずに聞き返した。私の指示が「内法 3600×2700 を壁の中心線で描く」で、矛盾していた。正しい保留(`results/sonnet-room-try1.txt`)。
   - 指示を「壁芯 3600×2700」に直すと、線4本・文字・画層2つを描き、読み戻して閉じた長方形を確かめ、保存した。26秒、13手番。
   - 前から残っていた線にも気づき、消さずに報告した(`results/try2-standard-font/`)。
3. つまずいたこと(連携側の失敗。AIの誤りではない)
   - mcp ライブラリ(Python 用の公式 SDK)が 2.x になり、FastMCP が MCPServer に改名されていた。私が 1.x の書き方で書いていたため、起動で止まった。2.x の書き方に直した。
   - 保存の窓に名前が入らず、`Untitled.dxf` で保存された。窓の名前の欄に直接書いて直した。
   - 日本語の文字が ◇ になった。書体 `standard` に漢字がないため。`unicode` を既定にした(`assets/librecad-room-standard-font.png` → `assets/librecad-room.png`)。

4. 必要な機能を一覧にし(`code/librecad-mcp/requirements.md`)、ほぼ全部を足した。
   - plugin の API にない機能(寸法を描く、元に戻す、DXF を開く、伸縮)は、本体の内部の関数を plugin から直接呼んで足した。
   - mac 版の LibreCAD は、C++ の関数を約11,000個公開していた。plugin が使う73個は、すべてその中にあった。
   - 道具は42個。測る・検証・差分は MCP server の側で計算する。
5. つまずいたこと(2回目)
   - 本体の画面の部品を返す関数の型を、私が読み違えて宣言した。DXF を開く命令で LibreCAD が落ちた。
   - 本体は 2.2.1.6 なのに、2.2.1 のソースで組んだ。部品の作りがずれて、また落ちた。版を合わせて直った。
   - 落ちたあとの起動では図面が開かず、plugin のメニューが押せなかった。build.sh で、新規を開いてから押すようにした。
   - 移動すると図形の id が変わり、続く操作が失敗した。結果に新しい id を返すようにした。
   - 状態を確かめる画面写真に、LibreCAD ではなくブラウザが写った。すぐ消し、以後は plugin の screenshot で図面の部分だけを撮った。
6. Sonnet に、#135 の家の図面で一連の流れを回させた(`results/e2e-stretch-validate/`)。
   - 開く → snapshot → stretch で東を 910 広げる → validate → 寸法の文字2件を直す → validate 0件 → 保存。22秒、12手番。
   - ただし、通り芯が1本斜めになった(`assets/e2e-after-stretch.png` の右端の赤い線)。stretch の窓に片端だけ入っていた。
   - validate はこれを見逃し、Sonnet も画像を開かなかった。validate に「傾いた線」の検査を足し、見つけられるようにした。
7. #135 の4課題を、10のモデルに MCP 経由で解かせ、DXF を直接扱った結果と比べた(`results/2026-11-05-135/`)。
   - 結論: 合計は MCP が 30点、DXF が 33.5点(40点満点)。道具を足しても、点は上がらなかった。Claude は時間が4〜6割に縮んだ。
   - 採点は `grades-C-mcp.json`、正解との比べは `check-C-mcp.json`。採点の決まりは #135(AIにDXFの寸法を変更させる)と同じ。
   - 4点満点の点数(MCP / DXF): Haiku 2.5 / 2.5、Sonnet 3 / 4、Opus 4 / 4、Fable 3 / 3.5、Luna 1 / 3、Terra 3 / 3、Sol 4 / 4、Astra 4 / 3、Flash 2 / 3.5、Argon 3.5 / 3。
   - 4課題の合計時間(MCP / DXF): Haiku 11 / 28分、Sonnet 9 / 16分、Opus 10 / 13分、Fable 14 / 23分。GPT は2〜6分でほぼ同じ。Gemini は40〜50分でほぼ同じ。
   - C-4(両立しない指示)は、10のモデルすべてが保存せずに確認した。DXF で寝室1の幅を読み違えた Argon も、今回は正しく読んだ。
   - Opus と Sol は4課題とも満点だった。Astra は C-2 を直せるようになり、Argon は C-4 を正しく保留した。
   - 点を落とした理由は、道具の失敗ではなく、直し漏れが多い。
     - Sonnet: C-2 でクローゼットの線を壁と一緒に動かさなかった。C-3 で屋根を直さずに保存した。
     - Fable: C-2 で北立面図の線が足りない。C-3 で通り芯Y5の丸印を元の位置に残した。
     - Argon: C-3 で Y5 の丸印を残した。stretch の窓に線は入り、丸の中心は入らなかったため。validate も丸印のずれは見ない。
   - Haiku の C-3 は、validate のあとに立面図を stretch し、検証し直さずに保存した。答えには「validate は違反なし」と書いた。保存した図面を開き直して validate すると、文字だけ古い寸法が6件出た。
   - Luna は、C-1 で LDK ではなく寝室1の窓を広げた。C-2 と C-3 も、指示から決められることを確認して止めた。
   - Flash は、C-2 と C-3 が20分で終わらなかった。C-3 では、MCP の作り(server.py)をシェルで読んで道具の使い方を探した。図面ファイルは読んでいない。
   - Terra は C-2 で「環境が読み取り専用なので保存できない」と止めた。MCP のときだけ、Codex の sandbox を read-only にしたためと見られる(DXF のときは workspace-write)。保存は LibreCAD が行うので、実際はできた。
   - 図面ファイルを直接読んだ回は、なかった。MCP 以外の道具は、Claude は道具の検索と画面写真の表示、Gemini は agy が保存した道具の結果と定義の読み取り、GPT は0回。
8. #138 の P(自作の平面図、8問)を、Claude 4つと Gemini 2つに MCP 経由で解かせた(`results/2026-11-05-138/`)。
   - 結論: 点はほぼ同じ。DXF でもほぼ満点で、上がる余地がなかった。
   - 採点は #138 と同じく、モデル名を伏せてサブエージェントに任せた(`grades-P.json`、`grading-P/`)。
   - 8点満点(MCP / DXF): Haiku 7.5 / 8、Sonnet 8 / 8、Opus 8 / 8、Fable 8 / 8、Flash 7 / 7.5、Argon 7.5 / 7.5。
   - 違いは P-4-1(寸法の値「1,200」と、図形の長さ 900 が食い違う)だけ。MCP は両方の値を返すのに、Haiku は 900 を確実として確認を求めず、Flash は 1,200 と断定した。
   - GPT の4つは、Codex の利用上限で流せなかった(各4秒で失敗。結果は消した)。
   - 1問あたり、Claude は数十秒、Gemini は1〜2分。
   - Claude は `--safe-mode` だと MCP も止まるため、`--setting-sources ""` で CLAUDE.md と memory を読ませずに流した。

時間: 最初の連携が約50分。機能の追加は、さらに約2時間。図面を描かせたのは1回30秒弱。

## 学び

- 本体を改造しなくても、plugin で LibreCAD の中の図面を操作できる。build は plugin 1つで、数秒で終わる。
- AI は道具の結果を読み戻して、自分で確かめた。DXF を書き換える方法では、この確認を AI が自分で組む必要があった。
- 道具が返さない情報は、AI も確かめられない。最初は文字の幅を返さず、中央寄せが見積もりになった(後で外形と中央寄せを足した)。
- 本体の内部を直接呼ぶと、plugin の API の外の機能も足せる。ただし本体と同じ版の header で組まないと落ちる。
- 検証の道具があると、AI は「直す → 検証 → 直す」を自分で回した。#135 の「文字だけ古い寸法」は、道具で見つけて直せた。
- 検証が見ない崩れは、AI も見逃す。画像を撮る道具があっても、指示しなければ見ない。
- 道具をそろえても、点は上がらなかった。速くはなった。点を分けたのは、直したあとに図面全体を見直すかどうかだった。
- 検証の道具は、最後の変更のあとに呼ばないと意味がない。Haiku は途中で呼んだ結果を、最後の答えに使った。
- 道具が食い違う2つの値を返しても、AI がそれを確認事項にするとは限らない。食い違いの扱いは、道具ではなく指示と AI の判断で決まる。
- 道具の外の条件(sandbox の設定)も、AI の判断を変える。読み取り専用と知らされた Terra は、保存できるのに止まった。
