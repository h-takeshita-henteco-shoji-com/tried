## 試したこと

AI市長が、いつ・何を見て・どう決めるかの型を決める。計画の「7〜9」と「19」を1件にまとめたもの。
先行研究(AIエージェントにゲームや街を運営させた例)を調べ、型の手がかりにする。

決めること:
- 判断の区切り: 1か月ごと(`advance(30)`)と、出来事ごと(`events`)の組み合わせ方
- 判断の前に見るもの: `city_info`、`economy`、`services`、市民の声(`citizens_summary`、`citizen_voices`、`complaints`)、画面写真
- 1回の判断で動かしてよい範囲と回数
- 市政ノート: 判断と理由、見た数字、結果を残す形式と置き場所
- 判断の前のセーブと一時停止の手順

成果物は、判断の型を書いた文書と、市政ノートの雛形。

## 結果

### 成果物

- 判断の型: `code/ai-mayor/mayor/protocol.md`(v1)
- 市政ノートの雛形: `code/ai-mayor/mayor/note-template.md`
- 市長の定義の雛形: `code/ai-mayor/mayor/mayor-template.md`
- 基準の市長の定義: `code/ai-mayor/mayor/mayors/base.md`
- AI市長の公約(暫定): `code/ai-mayor/mayor/pledges.md`(11個)
- `code/ai-mayor/docs/mcp-interface.md` の「判断の単位」は、型への案内に書き換えた

### コードを読んで分かった前提

- `advance(30)` は30日を一気に進め、途中で止まらない。出来事が起きた瞬間に止めることはできない
- `events` が返すのは、市民のつぶやき(Chirper)だけ。災害の警報や赤字の知らせは含まない
- 保存の道具はない。保存は人が行う決まり(#70)

### 決めた型(v1)

- 判断の区切りは3種類にした
  - 月例: 30日ごと。8つの道具で街を見て、施策を3件まで打つ
  - 見回り: 10日ごと。`city_info` と `events` だけを見る。施策は打たない
  - 臨時: 見回りで境目に当たったとき。施策は1件まで
- 1か月は `advance(10)` を3回に分けて進める。出来事で止められないので、10日ごとに見回る
- 臨時の境目は、つぶやきより数字を主にした
  - 所持金10,000未満、赤字への悪化、人口5%減、幸福度10以上の低下
  - 困りごとのつぶやき(火事、停電など)3件以上
- 月例で見る順は固定した。`city_info` → `economy` → `services` → `citizens_summary` → `complaints` → `citizen_voices(5)` → `events` → `screenshot`
- 動かす量の上限
  - 税は1回に±2ポイント、予算は±20ポイント、政策の変更は月1つ
  - 建設費は所持金の半分まで。維持費の増え分は週の黒字の範囲
  - 骨格(JR、西鉄、九州自動車道)は消さない。`pay=false` は使わない
- 市政ノート
  - 運営1回で1ファイル。日付フォルダの `mayor-note.md` に置く
  - 数字の表(月例と見回りで1行ずつ)と、判断の記録(答え合わせ、気づき、施策、次にやること)
  - 施策ごとに「予想」を書き、翌月に答え合わせをする
  - 月例の前に読むのは、数字の表、直前の月例、申し送りだけ
- 市長の定義と公約(ユーザーの提案で追加)
  - 公約は市長の性格の一部として、人が先に決める。市長は任期中に変えない
  - 公約は3つまで。ゲーム内の道具で測れる数字と期限で書く。#39 の「価値観は変えない」に合わせ、政治の立場の言葉は使わない
  - 施策ごとに、どの公約のためかを書く。月例の答え合わせで、公約の進み具合を見る
  - 基準の市長の公約は3つ。人口を毎月増やす、電気・水・下水が来ない市民をなくす、赤字を2回続けない
- AI市長の公約を11個、暫定で決めた。実現の方法は後続の回で考え、必要なら変える
  - 市長選の出馬表明者の公約と、福岡市の変遷を調べてから考えた
  - 案を3回尖らせた。最後は「今の福岡の特徴を1つ選び、ほかを犠牲にしてでも最大にする」形にした
  - 例: 那珂川を境に博多は商業だけ・福岡は住宅だけ、空港を天神のど真ん中に、毎月都心の1割を建て替える
  - どの市長に振るか、「1人3つまで」とどう合わせるかも、後続の回で決める
- 保存: 試運転(#73)では保存しない。本番(計画の20)の前に保存の道具を足す

### 先行研究

12件を調べた。型に効いたのは次の7件。CivBench と Hallucinating Splines は原文で数字を確かめた。

- CivBench(2026年9月、https://arxiv.org/abs/2609.02459): Civilization VI をMCPの道具76個で操作させた
  - 「20ターンごとに確かめよ」と指示しても、実際の確認は30〜75ターンごとだった
  - 計画に書いた約束が10ターン以内に実行されたのは、48.2〜65.8%
  - → 見る順を固定し、数字の表を埋めさせる。「次にやること」を答え合わせする
- Hallucinating Splines(2026年2月、https://dunn.us/notes/the-splines-are-hallucinating): Micropolis をAPIで操作する場。250超のAIが約1000の街を作った
  - 街の4分の1が破産した。維持費が税収を上回っていくことに気づけない
  - 建物の散らばりや、電力のつなぎ忘れが多い
  - → 建設費と維持費に上限。建てた後に、つながったかを確かめる
- Vending-Bench(2025、https://arxiv.org/abs/2502.15840): 自販機の運営。届く予定日を過ぎただけで「入荷した」と思い込み、脱線した
  - → ノートの結果の欄には、道具が返した事実だけを書く
- Project Vend(2025、https://www.anthropic.com/research/project-vend-1): 客に頼まれると値引きを繰り返した
  - → 税と予算の変更幅に上限
- Reflexion(2023、https://arxiv.org/abs/2303.11366): 結果を言葉で振り返り、次に渡すと上達する
  - → 予想と答え合わせ、申し送り
- Claude Plays Pokémon(2025): 履歴の要約で細部が消え、解決済みの場所に戻った
  - → ノートは要約せず、読む範囲を絞る
- Voyager(2023、https://arxiv.org/abs/2305.16291): うまくいった手順を部品として貯める
  - → v1には入れない。試運転の後に考える
- 他に確認したもの: Cradle(Cities: Skylines を画面写真とマウスで遊ぶ)、CivRealm、Generative Agents、ReAct、Factorio Learning Environment
- Cities: Skylines でLLMを評価する仕組み(benchmark)は見つからなかった

## 学び

- 型を決める前にコードを読むと、道具の制約が型を決めた。「出来事ごと」は、`advance` が止まらない以上、10日ごとの見回りで近づけるしかない
- AIは、指示した確認を省き、書いた約束の半分ほどしか守らない(CivBench)。確認は「表を埋める」という作業に変えると守らせやすい
- 月例の判断だけでは、その場の問題に引っぱられる。公約を先に決めると、判断に長い軸ができ、市長どうしの差も公約で比べられる
- 公約は、一般論の目標(人口、幸福度)より、街の特徴を極端にした方が尖る。福岡の歴史と今の姿を調べたことで、福岡でしか成り立たない公約になった
- 上達のためのノートには、理由より「予想」が要る。予想がないと、翌月に答え合わせができない
