## 試したこと

訪問介護の介護報酬のルール(告示・通知・Q&A)を根拠の箇所つきで引けるRAGを、複数の方式で作って比べる。
資料と問題集と採点は1つに揃え、方式だけを変える。器はSQLite 1つ(全文検索はFTS5、ベクトル検索はvec1)にする。
1件のフォルダで、何日かかけてすべての方式を比べる。コードは `code/kaigo-rag/` に置く。

比べる方式:

- 検索の基本: BM25(FTS5)、ベクトル検索(vec1)、両者を混ぜるハイブリッド(RRF)
- 検索を賢くする: リランカー、Contextual Retrieval、HyDE
- 検索をAIに任せる: エージェント検索
- ツリー索引をAIがたどる: PageIndex(VectifyAI/PageIndex)
- GraphRAG: 告示→通知→Q&Aの参照や、加算・サービスコードのつながりをたどる
- オントロジー: auto-ontology(NVIDIA/auto-ontology)。除外した。表の形のデータベースに対する NL-to-SQL の部品で、文書を引く今回の用途と合わない。Postgres と NVIDIA NIM の API キーも要る
- 取り込みの部品: LiteParse(run-llama/liteparse)。RAGの方式ではなく、PDFを文字にする部品として比べる

採点は、検索の質(recall@10)、答えの質、古い版での誤り、費用と速さの4つで行う。

### 1日目(2026-11-08): 土台から GraphRAG まで

上限は360分。資料の取り込み、問題集づくり、基本3種の比較までを予定した。時間が余ったため、検索を賢くする3種と、検索をAIに任せる2種(エージェント検索、PageIndex 方式)まで進めた。続けて、抜けていた老計10号と介護保険法を足して測り直し、GraphRAG を比べた。最後に、取り込みの部品として LiteParse を pdftotext と比べた。

#### 決めたこと

- 埋め込みモデルは `cl-nagoya/ruri-v3-310m`(768次元)を手元の M5(MPS)で動かす。API キーが要らず、vec1 の「端末の中で完結する」構想にも合う
- 生成役は Claude。`claude -p` をサブスクの範囲で使う
- vec1 は版0.8(SQLite 本体の `ext/vec1/vec1.c`)。構想を書いた時点の0.7から上がっていた。NEON、複数スレッドで動いた

#### 資料

- Q&A: 厚労省「介護サービス関係Q&A集」(令和8年9月掲載、Excel)。3,737行。「(上の行の続き)」で2行に分かれた問いをつなぐと3,722問
- 告示・省令・通知: 全老健「法令・Q&A検索システム」の溶け込み版。告示19号・95号・94号、省令37号、老企25号・36号の6本。約90万字
  - 厚労省の法令等データベースの老企36号は、平成12年の制定時の版だった(「家事援助」のまま)。最新は全老健の側にあった(令和8年3月13日更新)
- チャンク: 大きな見出し(章・節・条・第一・1・(1))で区切り、長いものだけ細かい項目(①・イ・注)で分けた。文書2,421件。見出しだけの小さな節は次の節に寄せた

#### 問題集

- 訪問介護の Q&A(158問)を乱数で分けた
- A 言い換え問題(100問): Sonnet に、問いをヘルパーやサ責のチャットの口ぶりに書き換えさせた。正解は元の Q&A(コーパスに残す)
  - 例: 「通院等のための乗車・降車の介助の前後に連続して行われる…身体介護…は別に算定できるのか。」→「通院の乗降介助をする前後に、部屋での着替えや病院の中の移動介助、トイレ介助も続けてやったんですが、それって身体介護として別に請求できるんですか?」
- B 根拠問題(40問): Q&A をコーパスから外し、問いそのものを使う。正解は答えの根拠になるチャンク
  - 答えの中で告示・通知の箇所を名指ししている訪問介護の Q&A は、160問中17問だけ。正解は付けるしかない
  - pooling: BM25・ベクトル・ハイブリッドの上位20件ずつを集め、Sonnet が公式の答えを見ながら 2/1/0 で判定した
  - 弱み: 集めた方式に有利に偏る。後の日にほかの方式が新しい根拠を引いたら、判定して足す
- コーパスは文書2,421件と Q&A 3,682件(B の40問を除く)で、計6,103件

#### 作ったもの

- SQLite 1ファイル(65MB)に、本文・FTS5・vec1(flat と ANN)を入れた。索引づくりは17秒
- BM25: fugashi(unidic-lite)で名詞・動詞・形容詞・副詞を取り、空白で区切って FTS5(unicode61)に入れた。問いは語の OR で引く
- ベクトル: vec1 の flat(厳密)と ANN(nbucket 80、codesize 32、opq、cos)。ANN は候補100件を取り、元のベクトルで並べ直す(rerank)
- ハイブリッド: BM25 とベクトル(ANN、nprobe 0.4)の上位100件ずつを RRF(c=60)で混ぜる

- 検索を賢くする3種(2日目の分を前倒し):
  - リランカー: `cl-nagoya/ruri-v3-reranker-310m`(cross-encoder)で、ハイブリッドの上位30件を並べ直す
  - HyDE: Sonnet に、問いごとに仮の答え(通知やQ&Aの文体、200字以内)を書かせる。仮の答えを文書として埋め込んで引く
  - Contextual Retrieval: Haiku に、文書チャンクごとの位置づけ(80字以内)を書かせ、本文の頭に足す。Q&A は種別と項目を機械的に足すだけ
    - 本家は文書全体を渡すが、1本15万字を超えるため、見出しのパスと直前のチャンクの抜粋だけを渡した
    - 対照として、見出しのパスを機械的に足す版(見出しパス)も作った
  - 生成の量: Contextual は2,421件を121回の呼び出し(4並列)で約30分。HyDE は139問を10回の呼び出しで数分

- 検索をAIに任せる2種(答えまで出す方式):
  - 答えの役はすべて Sonnet(`claude -p`)。道具は、モデルを読み込んだままの小さな HTTP サーバーと、Bash から呼ぶ CLI(`tool.py`)
  - RAG 一発(基準): ハイブリッド+リランカーの上位5件の全文を渡し、1回で答えさせる
  - エージェント検索: `search`(ハイブリッド+リランカーの上位8件)と `read`(全文)を渡し、何度でも引かせる
  - PageIndex 方式: `tree`(目次の1段)と `read` だけを渡す。検索語の照合も埋め込みも使わない。目次は、チャンクの見出しパスから作った(Q&A集は 種別 > 項目 > 問い)
    - 本家の PageIndex は、索引づくりと検索に LLM の API キーが要る(litellm 経由)。サブスクの `claude -p` では動かせないため、方式だけを再現した
    - 目次の出力を grep で絞ると検索になってしまうため、grep・rg・awk・sed を禁じた(1問目の試しで、grep を使っていた)
  - 比較の下限として、資料を渡さない「LLM だけ」も答えさせた
  - 答えを写させない工夫: 道具は資料の無い `/tmp` で動かし、Bash は道具の CLI だけを許した。B の問いと中身が同じ Q&A(写し)は、問いごとに道具から隠した
  - 答えの採点: Sonnet に、元の Q&A の答えと照らして 2/1/0 を付けさせた。1問ごとに4方式の答えを記号に置き換え、順番を混ぜて、方式を伏せた

- 資料の追加:
  - 老計10号: 厚労省は改正通知(平成30年、新旧対照つき)しか PDF で出していない。溶け込み版の全文は、枚方市が載せている PDF を使った。見出し(1―1―1 など)で切って28件
  - 介護保険法: 全老健の法令検索から取った。訪問介護の請求に関わる3章(総則、保険給付、事業者及び施設)だけで917件。附則と保険料・財政の章は外した
  - 既存の id を動かさないよう、コーパスの末尾に足した(計7,048件)。vec1 の ANN は、学習済みの区画にそのまま入れた(学習し直していない)
  - 足した資料のチャンクで、検索の上位20件に入った65件を判定して B の正解に足した。新たな判定2は1件だけ
  - そのうえで、RAG 一発・エージェント検索・PageIndex 方式に答えさせ直した。採点は、足す前の4方式と合わせた7つを、1問ごとにまとめて伏せて判定し直した

- GraphRAG(用語と参照のグラフ):
  - Microsoft の GraphRAG は、LLM で全チャンクから用語と関係を抜き出す。7,048件では残りの時間に収まらないため、LLM を使わずにグラフを作った
  - 用語: 見出し(「(22) 生活機能向上連携加算について」→「生活機能向上連携加算」)、Q&A の項目名、本文中の「〜加算」「〜介助」などから集めた。2〜400件のチャンクに出る1,144語
  - 用語のつながり: チャンクが用語を含めば辺を張る(33,588本)
  - 参照のつながり: 本文の「運営基準第25条」「法第8条」「留意事項通知第2の2(4)」を、参照先のチャンクにつないだ(522本。ほとんどが老企25号から省令37号への参照)
  - Q&A の答えが別の文書を名指しする例は、3,682問中およそ100問(3%)しかなかった。参照だけのグラフでは疎すぎるため、用語のつながりを主にした
  - グラフは同じ SQLite に表(entity、mention、ref)として入れた。作るのに3秒
  - 検索としての GraphRAG: 問いに含まれる用語と、ハイブリッドの上位3件が含む珍しい用語を起点にし、その用語を含むチャンクを珍しさ(idf)で点付けした。参照でつながるチャンクにも点を足した
  - エージェントとしての GraphRAG: エージェント検索の道具に `related` を足した。チャンクを渡すと用語と参照先を、用語を渡すとそれを含むチャンクを返す

### GraphRAG のライブラリ(LightRAG、Microsoft GraphRAG、HippoRAG 2)

1日目に作った GraphRAG は、LLM を使わない自前のグラフだった。ほかの GraphRAG も比べるため、GitHub のスター数と論文の情報量で3つ選んだ(2026-11-08 時点)。

| ライブラリ | スター | 方式 |
|---|---|---|
| HKUDS/LightRAG | 40.6k | LLM で用語と関係を抜き出し、用語と関係の2段で引く(EMNLP 2025) |
| microsoft/graphrag | 36.6k | GraphRAG の元の論文。用語のまとまり(community)ごとに LLM で要約を作る |
| OSU-NLP-Group/HippoRAG(HippoRAG 2) | 4.1k | 論文(NeurIPS 2024)の方式。用語のグラフを Personalized PageRank でたどる |

- 外したもの: getzep/graphiti(32.6k)は、エージェントの記憶向けで、時間で変わる事実を扱う。法令を引く用途とずれる。RAGFlow や LlamaIndex は、GraphRAG を機能の1つに持つ大きな枠組みなので外した
- 3つとも、索引づくりでチャンクごとに LLM を呼ぶ。7,048件では時間が収まらない。そこで、訪問介護の範囲だけを切り出した(608件、21万字)
  - 範囲: 訪問系の Q&A(訪問介護118、定期巡回81、夜間対応型38)、省令37号の第二章、老企25号の訪問介護、老企36号の訪問介護費、告示19号・94号・95号の訪問介護の部分、老計10号、介護保険法の総則
  - B のうち32問が、この範囲に正解(判定2)を持つ。正解も範囲の中だけで数え、基準の方式も同じ範囲で測り直す(`evaluate.py subset`)
- LLM は `claude -p`(索引づくりは Haiku)、埋め込みは ruri-v3。API キーは使わない
  - LightRAG は、LLM の関数を Python で差し込める。`claude -p` を直接呼ぶ(`src/graph_lightrag.py`)
  - Microsoft GraphRAG と HippoRAG は、OpenAI と同じ形の API で呼ぶ。手元に中継サーバー(`src/llm_shim.py`)を立て、LLM は `claude -p` に、埋め込みは ruri-v3 に渡す。2つとも別の環境に入ることまで確かめた(graphrag 3.3.0、hipporag 2.0.0a3)
- LightRAG の試し(8件): 176秒、LLM の呼び出し20回(1回約28秒)。用語は日本語で抜き出せた(「訪問介護費」「経過措置」など、1チャンクあたり約15語)
  - LightRAG は既定で文書を2件ずつしか並べない。`max_parallel_insert` を8に上げた。それでも同時に走る `claude -p` は6本前後で、608件に約100分かかる見込み
  - Haiku の出力に、LightRAG が決めた区切りの印が欠けることがある(「Complete delimiter can not be found」の警告)
- LightRAG の索引(608件): 2時間20分、LLM の呼び出し1,796回。用語3,441件、関係7,633件ができた
- LightRAG の引き方は5つある。naive はチャンクのベクトルだけ、local は用語から、global は関係から、hybrid は local と global、mix は hybrid とチャンクのベクトルを合わせる。naive 以外は、問いごとに LLM でキーワードを抜き出す
  - LightRAG が LLM に渡すはずのチャンクを、順番どおりに取り出して採点した(`aquery_data`)。答えは作らせていない
- Microsoft GraphRAG の索引(608件): 1時間40分、LLM の呼び出し約5,900回。用語5,629件、関係15,036件、用語のまとまり(community)1,467件と、その要約1,467件ができた
  - 既定の指示文は英語で出力させる。最初の8件の試しでは、用語も説明も英語になった。指示文に「日本語で書く」を足した(LightRAG は日本語の設定を持つ)
  - 用語の種類は、既定の4つ(組織、人、地名、出来事)に、サービス、費用、要件、書類を足した。一番多かったのは要件(2,247件)
  - 引き方は4つある。チャンクを LLM に渡すのは local(問いに近い用語から、用語・関係・要約・チャンクを集める)と basic(チャンクのベクトル検索)。global と drift は community の要約を渡すので、検索としては採点できない
  - local は、LLM に渡す文脈が12,000トークンを超えないように、チャンクの数を絞る。139問中59問で、渡すチャンクが10件に満たなかった
- HippoRAG 2 の索引(608件): 15分、LLM の呼び出し約1,230回(1件に2回。用語の抜き出しと三つ組の抜き出し)。用語3,266件、三つ組7,106件、言い換えの辺51,701本ができた
  - **HippoRAG は、用語をそろえるときに英数字以外を消す**(`[^A-Za-z0-9 ]` を空白にする)。日本語の用語は空か数字だけになり、8件の試しでは用語のノードが3つしかなかった。スクリプトの中で、Unicode の文字を残す関数に差し替えた(ライブラリ本体は書き換えない)。差し替えた後は100ノードになった
  - 部品の版が合わず(pyarrow が NumPy 2 を求める)、保存で止まった。pyarrow 16 を入れた
  - 引き方は2つ。HippoRAG 2(問いに近い三つ組を引き、LLM で選び直し、その用語から Personalized PageRank でたどる)と、DPR(チャンクのベクトル検索だけ)

## 結果

A は98問、B は30問で採点した(問いが空の Q&A と、根拠が0件の問いを除く)。

B の正解は、pool を2回に分けて付けた。1回目は基本3種の上位20件ずつ(1問平均35件)。2回目は、検索を賢くする方式が上位に出した未判定の499件を足した。2回目で新たに根拠とされたのは12件だけで、pool の偏りは小さかった。下の数字は2回目の後のもの。

### 検索の基本3種

| 方式 | A recall@1 | A recall@10 | A MRR@10 | B hit@10 | B recall@10 | B nDCG@10 | ms/問 |
|---|---|---|---|---|---|---|---|
| BM25(FTS5) | 0.60 | 0.91 | 0.706 | 0.77 | 0.59 | 0.532 | 7.5 |
| ベクトル(vec1 flat・厳密) | 0.82 | 0.98 | 0.876 | 0.90 | 0.66 | 0.549 | 8.3 |
| ベクトル(vec1 ANN・rerankなし・nprobe0.1) | 0.72 | 0.92 | 0.796 | 0.77 | 0.60 | 0.530 | 0.6 |
| ベクトル(vec1 ANN・rerankあり・nprobe0.1) | 0.80 | 0.95 | 0.854 | 0.87 | 0.62 | 0.527 | 0.5 |
| ベクトル(vec1 ANN・rerankあり・nprobe0.4) | 0.82 | 0.98 | 0.876 | 0.90 | 0.66 | 0.550 | 0.6 |
| ハイブリッド(RRF) | 0.81 | 0.99 | 0.871 | 0.83 | 0.59 | 0.593 | 7.7 |

- ベクトル検索が、A の1位(0.82)と B の10位以内(0.90)で最もよかった
- ハイブリッドは、A の10位以内(0.99)と B の nDCG(0.593)で最もよかった。B の10位以内ではベクトル単独に負けた
- BM25 は、言い換えた問いに弱い。BM25 だけが外し、ベクトルが引いた問いが8問あった。逆は3問
- ms/問は検索だけの時間。問いの埋め込み(ruri-v3)の時間は含まない

### 検索を賢くする3種

| 方式 | A recall@1 | A recall@10 | A MRR@10 | B hit@10 | B recall@10 | B nDCG@10 | ms/問 |
|---|---|---|---|---|---|---|---|
| 基準: ベクトル(ANN・nprobe0.4) | 0.82 | 0.98 | 0.876 | 0.90 | 0.66 | 0.550 | 3.3 |
| 基準: ハイブリッド | 0.81 | 0.99 | 0.871 | 0.83 | 0.59 | 0.593 | 8.3 |
| ハイブリッド+リランカー(上位30) | 0.91 | 0.97 | 0.923 | 0.93 | 0.74 | 0.644 | 1696 |
| 見出しパス(ベクトル) | 0.80 | 0.97 | 0.872 | 0.93 | 0.74 | 0.593 | 7.0 |
| 見出しパス(ハイブリッド) | 0.78 | 1.00 | 0.859 | 0.90 | 0.67 | 0.603 | 22.9 |
| HyDE(仮の答えでベクトル) | 0.40 | 0.90 | 0.577 | 0.87 | 0.67 | 0.607 | 2.7 |
| HyDE(問いと仮の答えの平均) | 0.74 | 0.97 | 0.834 | 0.90 | 0.73 | 0.614 | 1.0 |
| HyDE+BM25(ハイブリッド) | 0.76 | 0.99 | 0.840 | 0.87 | 0.65 | 0.613 | 7.2 |
| Contextual(ベクトル) | 0.83 | 0.97 | 0.891 | 0.90 | 0.65 | 0.586 | 6.1 |
| Contextual(ハイブリッド) | 0.78 | 1.00 | 0.858 | 0.87 | 0.65 | 0.607 | 18.9 |
| Contextual(ハイブリッド)+リランカー | 0.91 | 0.97 | 0.923 | 0.93 | 0.75 | 0.645 | 1590 |

- **リランカーが、ほぼすべての指標で最もよかった。** A の1位が0.81から0.91に、B の再現率が0.59から0.74に上がった。代わりに1問あたり約1.7秒かかる(手元の MPS、候補30件)
  - A の10位以内だけは0.99から0.97に下がった。候補をハイブリッドの上位30件に絞るため
- **HyDE は、問題の種類で効き方が逆になった。** A(問いが似た Q&A を探す)では、仮の答えだけで引くと1位が0.40に落ちた。B(根拠を探す)では、問いと平均すると再現率が0.66から0.73に上がった

- 告示・通知では、Contextual はハイブリッドで効いた(0.70→0.83)。足した文に検索語が増え、BM25 が拾いやすくなったと考えられる。ベクトルでは効かなかった
- 見出しパスでも0.80まで上がった。AI に書かせた文の上乗せは0.03で、19問では差と言い切れない
- HyDE も告示・通知には効いた(0.72→0.79)。仮の答えが通知の文体に寄るためと考えられる
- リランカーは、ここでも最もよかった(0.92、Contextual と重ねて0.94)

### 途中で見つけたこと

- **Q&A集の約半分は重複だった。** 3,722問のうち1,859問が、別のサービス種別に同じ問いと答えで載っている。A の23問、B の10問に写しがあった
  - 重複を数えない採点では、ベクトル検索の1位は0.65だった。中身が同じ Q&A を正解に数えると0.82になった。別の種別の写しを引いて、不正解にされていた
  - B では、外したはずの問いが写しとして残り、答えが漏れていた。採点で、写しを結果と正解の両方から除いた
- **根拠の多くは Q&A だった。** 1回目の判定で根拠(判定2)とされた145件のうち、116件が Q&A、29件が告示・通知(老企36号が20件)
- **資料の抜けがある、と最初は考えた。** 1回目の判定で根拠が0件だった6問の多くは、介護保険法や老計10号(訪問介護のサービス行為ごとの区分)に拠っていた。足して測り直すと、答えも検索もよくならなかった(上の「資料を足した後」)
- **埋め込みは束を小さくすると速かった。** 束16件では swap が18GBに達し、2時間超の見込みになった。束4件にすると6,103件が236秒で終わった。手元の M5 はメモリ16GBで、ほかに仮想マシンも動いていた


## 学び

- 採点の前に、正解の側を疑う。Q&A集の重複に気づかなければ、ベクトル検索を不当に低く見ていた
- 現場の言葉で聞くと、語の一致に頼る BM25 は落ちる。ベクトル検索がその差を埋めた
- vec1 の ANN は、rerank と nprobe の設定で結果が大きく動く。nprobe の1.0以上は区画の数になる点は罠になる
- 一番効いたのは、手元で動く小さなリランカーだった。AI に文を書かせる2つ(HyDE、Contextual)は、効く場面が限られた
- 文脈を足すなら、まず見出しのパスを機械的に足す。AI に書かせる文は、手間に見合う差が出なかった
- 「ルールを引く」と言っても、引けているのは主に Q&A。告示・通知を引く力は、分けて測らないと見えない
- 答えの採点では、点だけでなく外し方を見る。LLM だけと RAG 一発は同点だったが、片方は結論を取り違え、片方は「分からない」で止まった
- AI に引き直させると、上位5件で足りない問いを拾えた。目次をたどるだけでも同じ正答数に届いたが、手数は3倍かかった
- 「資料が足りないから外れる」は、足して確かめるまで仮説にすぎない。今回は、外れの原因は問いと答えの形にあった
- AI に判定させるなら、同じ答えを2回判定させて、ぶれの幅を先に測る。ぶれより小さい差は、方式の差と言えない
- PDF の部品は、文字の中身より、構造と段組みで差が出る。LiteParse は見出しを付けてくれる一方、日本語に空白を入れ、新旧対照表を混ぜるページがあった
- GraphRAG は、検索の部品としては効かなかった。エージェントの道具として渡すと、効いた問いがあった。同じグラフでも、使い方で評価が変わる
- 法令のグラフは、LLM に抜き出させなくても、見出しと「〜加算」の字面から3秒で作れた。参照の名指しは少ないので、用語でつなぐほうが辺が多い
- LightRAG は、LLM で用語と関係を抜き出しても、検索の点を上げなかった。グラフの候補は、問いの根拠でないチャンクを連れてくる。グラフを検索に混ぜる前に、グラフだけの点を測る
- GraphRAG のライブラリを3つ試して、グラフで点が上がったものはなかった。LightRAG と Microsoft GraphRAG はグラフなしが一番で、HippoRAG 2 もグラフなしとの差は0.01だった。法令と Q&A を引く用途では、LLM でグラフを作る手間に、検索の点が見合わない
- 3つ目の HippoRAG 2 で一番よく見えた差は、グラフではなく前処理(改行を空白にする)から来ていた。ライブラリを比べるときは、グラフを使わない引き方も同じライブラリの中で測り、差を分ける
- ruri-v3 は、文中の改行で点が下がった。埋め込む前に改行を空白にするだけで、B の再現率が0.08上がった
- 英語圏のライブラリは、日本語を黙って壊すことがある。指示文の出力が英語に固定されていたり(Microsoft GraphRAG)、英数字以外を消したり(HippoRAG)する。8件で試して、抜き出しの中身を見てから全件に進む
- ライブラリの裏で LLM を呼ぶときは、空の応答を数える。`---` で始まる指示文が CLI のオプションと取り違えられ、エラーにならず空で返っていた
- ぶれは判定だけでなく、答えの側にもある。エージェントは、答えさせるたびに検索の仕方が変わる。39問では、揺れだけで5問の差が出た
